# Evaluation dataset contract

This describes exactly what `evaluation/datasets.py` reads when you point the
harness (`python -m evaluation --dataset ...`) at your own labelled photos. It
is derived directly from that module's parsing code — nothing here is a
proposed format; it is what `load_folder` and `load_pairs_csv` actually
require. See [`docs/evaluation.md`](evaluation.md) for how to run the harness
once you have a dataset in one of these shapes.

There is no company-specific export tool in this template: build one of the
two layouts below from whatever system holds your labelled face pairs.

## Option A: `folder:PATH`

```
PATH/
  <identity-1>/
    reference.jpg        # optional: this identity's reference photo
    probe-0001.jpg
    probe-0002.jpg
  <identity-2>/
    ...
```

Parsed by `load_folder` (`evaluation/datasets.py`):

- One subdirectory of `PATH` per identity. The subdirectory name is used
  verbatim as the identity label (see **Pseudonymising identities** below —
  the harness does not hash or otherwise transform it).
- Every file directly inside an identity's directory is one image, keyed as
  `"<identity>/<filename>"`. Hidden files (dotfiles) and non-file entries are
  skipped, as are hidden identity directories.
- Only files whose suffix (case-insensitive) is one of `.jpg`, `.jpeg`,
  `.png`, `.bmp`, `.webp` are read (`IMAGE_SUFFIXES`); anything else in the
  directory is ignored.
- **Reference photo:** if a file's stem (filename without extension) is
  exactly `reference` (case-insensitive — e.g. `reference.jpg`,
  `Reference.PNG`), that image is marked as the identity's reference photo.
  This changes how genuine pairs are built (`evaluation/scoring.py`,
  `_derived_genuine`):
  - **If the identity has a reference photo:** genuine pairs are
    reference-vs-every-other-photo for that identity (the reference is never
    paired against itself, and non-reference photos are not paired against
    each other).
  - **If the identity has no reference photo:** every pair of photos within
    that identity is treated as a genuine pair.
  - **A dataset must not mix the two** within itself: if some identities have
    a reference photo and others don't, `build_pairs` raises an error rather
    than silently mixing reference-vs-probe pairs with probe-vs-probe pairs.
    Give every identity a reference photo, or none.
- At least one image must be found under `PATH`, or `load_folder` raises
  `ValueError`.
- Impostor pairs are not read from the folder at all — they are generated by
  the harness (`evaluation/scoring.py`'s `_cross_identity`, controlled by
  `--max-impostors`, `--seed`, `--augment-impostors`; see
  `docs/evaluation.md`).

## Option B: `pairs:CSV`

Explicit pairs, for when you already know which photos should and shouldn't
match and don't need the harness to derive pairs from identity groupings.

Required header, exactly (`load_pairs_csv`, `evaluation/datasets.py`):

```
image_a,image_b,same
```

- **`image_a`, `image_b`** — paths to the two images being compared, resolved
  relative to the CSV file's own directory (not the current working
  directory).
- **`same`** — whether the pair is genuine (same identity) or an impostor
  pair (different identities). Accepted values, case-insensitive, leading/
  trailing whitespace stripped:
  - genuine: `1`, `true`, `yes`, `same`
  - impostor: `0`, `false`, `no`, `different`
  - anything else raises `ValueError`.
- A missing column in the header (any of the three) raises `ValueError`
  naming the missing column(s).
- Every image path referenced by any row must exist on disk relative to the
  CSV's directory; if any are missing, `load_pairs_csv` raises
  `FileNotFoundError` naming the count and one example.
- This dataset has no separate identity/reference concept: `identity` is
  empty, so `--augment-impostors` (which needs identities to derive
  additional cross-identity pairs) cannot add anything beyond the pairs the
  CSV lists explicitly.

## Where files live

Nothing under this repository's version control. `eval_data/`, `eval_out/`
and `.eval_cache/` are gitignored (see `docs/evaluation.md` §3) because they
hold face images, embeddings and comparison reports — treat all of it as
biometric data: never commit it, attach it to a PR, or paste it into chat,
tickets or logs.

## Pseudonymising identities

The harness itself does not pseudonymise anything — whatever string you use
as a directory name (Option A) or bake into an image path (Option B) is used
as-is as the identity label in reports, quality summaries and bootstrap CIs.
If your source data has real names, internal user IDs, or anything else that
identifies a real person, replace that identifier with a pseudonym
*before* it ever becomes a directory name or file path under `eval_data/`:

- Derive the pseudonym as a keyed hash of the real identifier — e.g.
  `hexdigest(hmac_sha256(salt, real_id))[:N]` — not a reversible encoding
  (base64, a sequential counter tied to a lookup table you keep, etc.).
- Generate the salt once with a real CSPRNG (e.g.
  `python -c "import secrets; print(secrets.token_hex(32))"`), at least 16
  characters, and save it to a file outside the repository with restrictive
  permissions (`umask 077`).
- **Never commit the salt, or check it into anything that reaches this
  repository.** It is what makes the pseudonyms non-reversible; treat it like
  a credential.
- Reuse the same salt across exports (rather than generating a fresh one each
  time) so the same real person maps to the same pseudonym on every run —
  otherwise you cannot compare results across two exports, or accumulate more
  probe photos for an existing identity.
- Delete `eval_data/` and `.eval_cache/` when you are done with a run (they
  regenerate cheaply from your source system); the salt file is the only
  piece of this that needs to persist.
